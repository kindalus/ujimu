Slice 12

Passkeys post-MVP

Add passwordless WebAuthn/passkey sign-in after the OTP MVP is stable.

post-MVP WebAuthn account security OTP fallback
Idea

Passkeys improve security without adding passwords.

Users who already have an account can register a device-backed credential and use it for future sign-ins.

Timing

This is deliberately after OTP.

  • OTP by email and mobile phone is the MVP authentication path.
  • Passkeys should reuse the same user and session model.
  • Do not block the MVP on browser-specific passkey complexity.
  • Keep OTP as fallback for account recovery and unsupported devices.
Refined direction

Passkeys are for every registered user.

  • Do not limit passkeys to subscribers or administrators.
  • OTP remains the account bootstrap, fallback, and recovery path.
  • Passkey management lives in a dedicated account-security page, not inside the chat workspace.
  • The target experience is: add passkey after OTP sign-in, sign out, sign back in with passkey, remove passkey, and still use OTP.
User flows

Registration and sign-in are separate flows.

Register passkeyAuthenticated registered user adds a passkey from /account/security.
Sign inUser chooses passkey sign-in and completes the browser authenticator flow.
Remove passkeyUser removes a registered credential while retaining OTP access.

Security conditions

WebAuthn checks must be strict.

  • Validate origin and relying-party ID against configured production values.
  • Use one-time challenges with short expiry.
  • Bind credentials to the authenticated user during registration.
  • Reject replayed or malformed assertions.
  • Never expose private keys because the app never receives them.
Implementation boundary

Use a WebAuthn library behind a swappable contract.

  • Use a mature WebAuthn/passkey library rather than hand-rolling cryptographic verification.
  • Keep library-specific calls behind an internal passkey service/adapter so the implementation can be replaced later.
  • Verify official library documentation before implementation and keep origin/RP configuration explicit.
  • Reuse the existing user and JWT session model after successful passkey login.

MVP scope

Small enough to verify, useful enough to keep.

In scopePasskey registration for authenticated users, passkey login, credential listing/removal, OTP fallback, strict challenge/origin checks, and tests around replay/expiry failures.
Not doingNo passwords, no mandatory passkeys, no passkey-only accounts, no admin-only rollout, no enterprise SSO, and no recovery path that removes OTP.
Success conditions

What must be true when the slice is done.

  • A registered OTP user can add a passkey from /account/security.
  • The user can sign out and sign back in with the registered passkey, without requesting a new OTP.
  • The user can remove the passkey and that credential can no longer sign in.
  • OTP continues to work after adding or removing passkeys.
  • Invalid origin, expired challenge, or replayed assertion does not create a session.

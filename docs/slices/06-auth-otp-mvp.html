Slice 6

Authentication with OTP

Allow users to register and sign in using one-time passwords by email or mobile phone.

email OTP SMS OTP SendGrid sessions passkeys later
Idea

Account creation should feel lightweight.

The MVP avoids passwords. Users identify by email or phone, receive a temporary code, and get a secure session after verification.

Flows

Two login channels, one account model.

EmailUser enters email, receives code, verifies code, session starts.
Mobile phoneUser enters phone number, receives code, verifies code, session starts.
LinkingThe same user can later attach the other contact method when verified.
Provider abstraction

SendGrid first, replaceable later.

  • Hide email/SMS delivery behind provider interfaces.
  • SendGrid is the preferred initial provider where applicable.
  • Changing provider should not alter OTP business logic.
  • Delivery failures are visible to the user without leaking internal provider errors.
OTP lifecycle

Codes are short-lived and limited.

  • Store OTP secrets hashed, never plaintext.
  • Use a configurable expiry window; initial default is 10 minutes.
  • Limit verification attempts per code.
  • Allow controlled resend without creating unlimited codes.
Sessions

Sessions are server-owned.

  • Use secure, httpOnly cookies for browser sessions.
  • Initial default: sessions expire after 30 days of inactivity unless configured otherwise.
  • Logout invalidates the active session.
  • Session identity becomes the subject for quotas and history.
Out of scope

Passkeys are deliberately deferred.

The data model should not block passkeys, but passkey registration and authentication belong to a later slice.

Likely implementation areas

Auth lives on the server boundary.

Success conditions

What must be true when the slice is done.

  • A new user can sign in with a verified email OTP.
  • A new user can sign in with a verified mobile-phone OTP.
  • Expired, reused, or over-attempted codes do not create sessions.
  • Provider-specific delivery code is isolated behind an interface.
  • Authenticated users are recognised by quota and history slices.

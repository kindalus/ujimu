Slice 8

Admin specialist management

Provide an admin-only console for creating, editing, uploading to, reloading, auditing, and deleting specialists.

admin allowlist single page uploads manual ingest audit
Idea-refined direction

Admins manage public knowledge domains without code changes.

The admin area should turn specialist directory, YAML, raw source, ingestion-status, and destructive deletion operations into safe product workflows.

Role model

One role, bootstrapped by environment.

There is only admin. A verified OTP user becomes admin only when one of their verified contacts appears in an environment allowlist such as UJIMU_ADMIN_CONTACTS.

No editor, reviewer, owner, per-specialist permission model, or in-product admin management is needed in this slice.
Create specialist

Creation writes the disk contract.

  • Collect ID, display name, description, LLM Wiki preset, system prompt, citations-required, and streaming-enabled settings.
  • Create specialist.yaml and required directories atomically enough to avoid half-created public specialists.
  • Load the new specialist into the registry immediately.
  • Reject duplicate IDs, invalid slugs, and unsupported wiki presets.
  • Keep visibility out of scope: created specialists are public once valid and loaded.
Edit specialist

Metadata and prompts are editable.

  • Admins can edit display metadata and system prompts.
  • Prompt changes do not require audit history in the MVP.
  • Changes should trigger a safe reload of the affected specialist.
  • Invalid edits must not leave YAML half-written.
Upload and ingest

Uploads land in raw/; ingestion is explicit.

admin selects specialist
→
uploads file
→
file stored in raw/
→
source detected as pending
→
admin runs ingestion manually
Upload should not silently run Pi ingestion. A separate reload/detect action refreshes state, and a separate ingestion action may run only when ingestion is enabled.
Delete specialist

Deletion has product-wide consequences.

  • Remove the specialist from the selectable list.
  • Delete customer histories for that specialist.
  • Remove or quarantine the specialist directory according to the destructive-delete implementation.
  • Require explicit admin confirmation before deletion.

Success conditions

What must be true when the slice is done.

  • Unauthenticated users and non-allowlisted registered users cannot access admin specialist operations.
  • An allowlisted admin can create a valid legislation/regulatory specialist through the single-page UI.
  • An admin can upload a source file, refresh detection, and see it marked pending for ingestion.
  • An admin can manually run ingestion when enabled and inspect source statuses.
  • An admin can edit specialist metadata and prompt without prompt-version audit history.
  • Deleting a specialist requires explicit confirmation, removes it from chat selection, and deletes associated customer histories.
  • Admin create/edit/upload/reload/delete actions create minimal audit events in SQLite.

ArquitecturaFontes, ingestão e acesso restricto
Origem

Arquitectura incremental

Desenho técnico para implementar docs/specs/brainstorm-admin-source-ingestion-access.html sem reescrever o produto: manter Nuxt, SQLite, ficheiros de especialista e Pi, acrescentando metadados, permissões e jobs persistentes.

Base aceite

Manter a arquitectura existente

  • specialist.yaml continua a ser a fonte de metadados e runtime settings do especialista.
  • raw/, wiki/ e ingest/state.json continuam a existir por especialista.
  • SQLite continua a guardar utilizadores, histórico, analytics, auditoria e passa a guardar a fila recuperável.
  • Pi continua a executar conversão e ingestão quando os flags correspondentes estão activos.
  • Validação e autorização continuam no servidor; a UI apenas reflecte estados.
Modelo do especialista

Estado e visibilidade no YAML

specialist.yaml
  status: active | suspended
  allowed_emails:
    - pessoa@exemplo.ao

Regra:
  status omitted => active
  allowed_emails omitted or [] => público
  • O admin pode editar status e uma textarea com um email por linha.
  • A API pública só devolve especialistas activos acessíveis ao utilizador actual.
  • O chat, a listagem de histórico e a retoma de conversa validam acesso no servidor.
Autorização por especialista

Uma função central de acesso

  • Criar utilitário server-side: canUseSpecialist(specialist, subject).
  • Especialista suspenso: invisível e indisponível para todos os não-admins.
  • allowed_emails vazia: acesso público para anónimos e autenticados.
  • allowed_emails preenchida: exige utilizador autenticado com identidade verificada correspondente.
  • Endpoints de admin continuam protegidos por requireAdmin e podem ver todos os especialistas.
Fontes oficiais

Upload e substituição como uma operação

  • Upload novo grava o ficheiro em raw/ usando a convenção segura existente.
  • Upload com o mesmo nome lógico substitui a fonte actual e marca internamente a fonte anterior como substituída.
  • A versão antiga não precisa de aparecer na UI, mas a auditoria regista acção, nome e tamanho.
  • Após upload/substituição, o estado da fonte fica pendente de ingestão, sem botão de conversão.
  • O botão global “recarregar fontes” passa a ser “Actualizar estado”, lendo apenas o estado actual das fontes oficiais.
Pipeline

Conversão é etapa interna da ingestão

  • O endpoint de conversão manual deixa de ser usado pela UI e fica candidato a remoção/depreciação em slice próprio.
  • O worker de ingestão faz: detectar/normalizar fonte → converter se necessário → validar Markdown → ingerir para wiki.
  • Estados existentes conversion e ingestion podem continuar em ingest/state.json para compatibilidade visual e debug.
  • Se conversão falhar, a fonte fica com erro de conversão e a ingestão fica bloqueada/falhada sem prender a UI.
Fila recuperável

Jobs persistidos em SQLite

background_jobs
  id TEXT PRIMARY KEY
  type TEXT CHECK ('specialist_ingestion')
  specialist_id TEXT NOT NULL
  status TEXT CHECK ('queued','running','succeeded','failed','cancelled')
  attempts INTEGER NOT NULL
  max_attempts INTEGER NOT NULL
  locked_at TEXT
  locked_by TEXT
  last_error_code TEXT
  last_error_message TEXT
  created_at TEXT
  updated_at TEXT
  completed_at TEXT
  • O comando “Executar ingestão” cria job e responde imediatamente com 202.
  • Ao arrancar, jobs queued ou running antigos podem ser retomados por worker recuperável.
  • Um lock simples evita dois workers no mesmo job.
Worker

Background sem bloquear o pedido

  • O endpoint admin chama enqueueSpecialistIngestionJob e dispara runDueBackgroundJobs sem aguardar o Pi.
  • O worker abre a sua própria ligação SQLite e fecha-a ao terminar.
  • O estado visível ao admin vem de ingest/state.json mais último job relevante.
  • Para testes, o worker aceita runner fake e relógio injectável.
  • Em produção simples, o worker pode correr in-process, mas a fonte de verdade é a tabela persistida.
Contratos API

Superfícies a mudar

  • GET /api/specialists: filtra por sessão/contacto e só expõe especialistas activos acessíveis.
  • POST /api/admin/specialists/:id/raw: aceita upload inicial ou substituição controlada.
  • POST /api/admin/specialists/:id/ingestion/run: devolve 202 com job, não resultado final.
  • POST /api/admin/specialists/:id/sources/reload: substituir por refresh de estado; manter rota inicialmente como alias se necessário.
  • PATCH /api/admin/specialists/:id: aceita status e allowed_emails.
UI admin

Menos acções, mais estado

  • Lista de especialistas mostra badges activo/suspenso e restricto/público.
  • Ficha do especialista adiciona selector/switch de suspensão e textarea de emails permitidos.
  • Zona de fontes oficiais mostra upload/substituição, “Executar ingestão” e “Actualizar estado”.
  • Remover da UI “Executar conversão” e “Recarregar fontes”.
  • Mensagens dizem que ingestão foi agendada, não concluída.
Segurança

Barreiras obrigatórias

  • Não confiar em lista pública de especialistas no cliente; chat e histórico revalidam acesso.
  • Normalizar emails para comparação case-insensitive e trim; rejeitar linhas inválidas no admin.
  • Uploads continuam limitados por extensão, content-type compatível e caminho dentro de raw/.
  • Não devolver allowlist a utilizadores públicos; só admin vê emails permitidos.
  • Não expor conteúdo da fonte, prompts, segredos ou stack traces nos erros de job.

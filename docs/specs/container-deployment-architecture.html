Architecture

Podman deployment shape

A single immutable Ujimu image, two runtime profiles, host-persisted Pi and Ujimu data, and small lifecycle scripts that make manual deploys repeatable.

Source

Derived from approved brainstorm

  • Brainstorm deck: docs/specs/brainstorm-container-deployment.html.
  • One image serves production and test profiles.
  • Test profile uses existing in-code mock/no-op provider paths.
  • CI/CD is deferred until the manual deployment contract is proven.

Runtime layout

Host data survives redeploys

  • Image creates and runs as Unix user/group ujimu:ujimu.
  • The in-container Ujimu home directory is /home/ujimu.
  • Mount production host storage from /srv/ujimu/prod/pi and /srv/ujimu/prod/data.
  • Mount test host storage from /srv/ujimu/test/pi and /srv/ujimu/test/data.
  • Inside the container, both profiles use /home/ujimu/.pi and /home/ujimu/.local/share/ujimu.
  • Set UJIMU_DATA_DIR=/home/ujimu/.local/share/ujimu inside the runtime environment.

Test isolation

Environment selects existing no-op paths

  • Auth: enable fake OTP delivery only where the app permits non-production fake delivery.
  • Billing: use the existing mock checkout/provider boundary.
  • Communication: do not configure SendGrid or other real outbound providers in test env.
  • Passkeys and external integrations remain disabled unless deliberately enabled.
Timezone

Default Africa/Luanda, override by ENV

  • Container should default TZ=Africa/Luanda.
  • Env files may override TZ for another IANA timezone.
  • Application-level quota logic already falls back to Africa/Luanda for invalid/missing user timezones.
Scripts

Small commands over orchestration

  • build.sh builds/tags the Ujimu image.
  • create.sh prod|test creates network, directories, and a stopped container.
  • deploy.sh prod|test creates if needed, then starts/restarts.
  • redeploy.sh prod|test rebuilds, replaces the container, and preserves mounted data.
  • remove.sh prod|test removes only the container, never persistent host data.
Non-goals

Keep this slice narrow

  • No CI/CD pipeline yet.
  • No TLS, reverse proxy, domain, or certificate automation.
  • No new auth/payment/communication provider implementations.
  • No backup scheduler; document backup expectations only if needed.
  • No Kubernetes/Compose abstraction unless Podman scripts become insufficient.
Open design questions

Need alignment before slicing

  • Resolved: use fixed in-container runtime home /home/ujimu.

  • Resolved: prod and test use the same in-container mount points.
  • Resolved: deployment maps those mount points to /srv/ujimu/prod/* and /srv/ujimu/test/* host locations.
Iteration log

Architecture iteration 1

  • Inspected existing provider boundaries: fake OTP delivery, mock billing checkout, Pi config envs, and Ujimu data-dir defaults.
  • Captured a single-image, two-profile architecture with mounted persistent Pi/Ujimu state.
  • Deferred CI/CD and reverse proxy concerns to keep this deployment feature focused.
  • Iteration 2: user chose fixed /home/ujimu in-container paths and internal image user/group ujimu:ujimu.
  • Iteration 3: clarified that prod/test share the same in-container mount points but map to different host volumes at deployment time.
  • Iteration 4: user confirmed host conventions /srv/ujimu/prod/pi, /srv/ujimu/prod/data, /srv/ujimu/test/pi, and /srv/ujimu/test/data.

Brainstorm

Container deployment

Define the smallest reliable Podman-based deployment shape for Ujimu, with separate production and test containers and persistent Pi/wiki data across redeployments.

Objective

Make deployment repeatable

  • Create Dockerfile/container build artefacts for Ujimu.
  • Add scripts for create, deploy, and redeploy operations under Podman.
  • Support production and test runtime modes.
  • Persist Pi configuration and Ujimu wiki/application data across image and container replacement.
Known decisions

Decisions already stated

RuntimeContainers run in a Podman environment; Dockerfile-compatible build files are acceptable.
Two modesProduction and test containers must be creatable as distinct runtime profiles.
Test isolationTest containers must not link to external auth, payment, or communication systems.
PersistenceUse ~/.pi for Pi state and ~/.local/share/ujimu for Ujimu wikis/data.
Governing context

Repository constraints to respect

  • Persistent app data defaults under UJIMU_DATA_DIR, including SQLite and specialties.
  • Pi enable flags must explicitly gate conversion, ingestion, and chat.
  • Secrets must remain outside source control and logs.
  • Pi resources currently live under config/ujimu-pi-agent/; runtime credentials must not be committed.
  • Operational quality gate: npm ci, tests, typecheck, build, and high-severity audit.
Direction chosen

Single image, different environments

ImageOne production-grade image built from the repo, parameterised by environment variables at runtime.
Prod containerExternal integrations enabled only through explicit secrets and provider variables.
Test containerUses internal mock/no-op providers for auth, payments, and communication.
Decision: avoid separate Dockerfiles or images for prod/test unless implementation proves the single-image path unsafe or impractical.
Operational decisions

Script defaults are now concrete

  • Container names: ujimu-prod and ujimu-test.
  • Network name: ujimu.
  • Ports: production on 3000, test on 3001.
  • Deployment should create/use both a Unix user and group for Ujimu; exact pair assumed as ujimu:ujimu unless corrected.
  • TLS and reverse proxy are explicitly outside this feature scope.
Iteration log

Iterations 1–2

  • Iteration 1: captured Podman containerisation, Dockerfile, lifecycle scripts, two runtime modes, and persistent Pi/Ujimu data.
  • Iteration 2: user chose a single image with prod/test env variables.
  • Iteration 2: test mode must use internal mock/no-op providers for auth, payments, and communication.
  • Iteration 2: scripts should standardise container names, network, and ports; reverse proxy/TLS stays out of scope.
  • Iteration 2: image must include Gemini CLI via npm install -g @google/gemini-cli.
  • Iteration 3: runtime timezone must be configurable by environment variable and default to Africa/Luanda.
  • Iteration 4: user approved the proposed lifecycle script names and env example file convention.
  • Iteration 4: CI/CD is intentionally deferred until manual Podman deployment is stable.
  • Iteration 5: user confirmed the feature should use existing in-code mock/no-op providers rather than create new ones.
Script contract

Lifecycle scripts approved

  • scripts/container/build.sh
  • scripts/container/create.sh prod|test
  • scripts/container/deploy.sh prod|test
  • scripts/container/redeploy.sh prod|test
  • scripts/container/remove.sh prod|test
Configuration contract

Env examples, real secrets outside Git

  • Version examples under config/container/prod.env.example and config/container/test.env.example.
  • Real prod.env and test.env should live on the server and stay out of source control.
  • Timezone defaults to Africa/Luanda and can be overridden by ENV.
  • Persistent host paths are ~/.pi and ~/.local/share/ujimu.
CI/CD decision

Not in this slice

CI/CD should be deferred until manual Podman deployment is stable. This feature may keep the deployment contract CI-friendly, but should not add automatic build/deploy pipelines yet.

Reason: avoid automating an operational shape before build, persistence, redeploy, and test isolation have been validated manually.
Boundary

Use existing no-op providers

The container feature should use the mock/no-op auth, payment, and communication paths that already exist in code. It should not introduce new provider implementations unless implementation proves a required switch is missing.

Scope guard: container work wires the existing runtime modes; it does not redesign provider abstractions.

Slice 12

Passkeys post-MVP

Add passwordless WebAuthn/passkey sign-in after the OTP MVP is stable.

post-MVP WebAuthn account security OTP fallback
Idea

Passkeys improve security without adding passwords.

Users who already have an account can register a device-backed credential and use it for future sign-ins.

Timing

This is deliberately after OTP.

  • OTP by email and mobile phone is the MVP authentication path.
  • Passkeys should reuse the same user and session model.
  • Do not block the MVP on browser-specific passkey complexity.
  • Keep OTP as fallback for account recovery and unsupported devices.
Refined direction

Passkeys are for every registered user.

  • Do not limit passkeys to subscribers or administrators.
  • OTP remains the account bootstrap, fallback, and recovery path.
  • Passkey management lives in a dedicated account-security page, not inside the chat workspace.
  • The target experience is: add passkey after OTP sign-in, sign out, sign back in with passkey, remove passkey, and still use OTP.
User flows

Registration and sign-in are separate flows.

Register passkeyAuthenticated registered user adds a passkey from /account/security.
Sign inUser chooses passkey sign-in and completes the browser authenticator flow.
Remove passkeyUser removes a registered credential while retaining OTP access.
Locked data model

Store credentials without storing secrets.

passkey_credentials
  id, user_id, credential_id UNIQUE, public_key
  counter, transports_json, created_at, last_used_at
  deleted_at, deleted_by_user_id

passkey_challenges
  id, challenge UNIQUE, purpose, user_id
  created_at, expires_at, consumed_at, metadata_json

passkey_auth_attempts
  id, subject_type, subject_id, purpose
  success, failure_code, occurred_at
Locked security

WebAuthn checks must be strict.

  • Passkeys are enabled explicitly and require configured origin/RP values in production.
  • Registration requires a session created by OTP within the last 15 minutes.
  • Use one-time five-minute challenges consumed on any verification attempt.
  • Validate origin/RP ID, bind credentials to the current user, and reject replayed or malformed assertions.
  • Rate-limit public login endpoints and validate same-origin on authenticated passkey mutations.
Implementation boundary

Use SimpleWebAuthn behind a swappable contract.

  • Use @simplewebauthn/server and @simplewebauthn/browser initially.
  • Keep library-specific calls behind an internal PasskeyWebAuthnAdapter.
  • Tests inject a deterministic fake adapter instead of real browser/OS authenticators.
  • Reuse the existing user and JWT session model, extended with authMethod.
Locked endpoint contract

Challenge creation is always POST.

POST /api/auth/passkeys/registration/options
POST /api/auth/passkeys/registration/verify
POST /api/auth/passkeys/authentication/options
POST /api/auth/passkeys/authentication/verify
GET    /api/auth/passkeys
DELETE /api/auth/passkeys/:credentialId
Options responses expose WebAuthn options only. The server stores and looks up challenges by challenge value and purpose.

Locked WebAuthn policy

Modern passkeys, conservative trust.

  • Registration uses attestation none, residentKey preferred, userVerification preferred.
  • Login uses discoverable credentials: do not send allowCredentials.
  • Registration sends active credentials in excludeCredentials.
  • Credentials are soft-deleted and may be reactivated only for the same user.
  • Counter checks reject non-increasing positive counters but accept always-zero authenticators.
MVP scope

Small enough to verify, useful enough to keep.

In scopePasskey registration for authenticated users after recent OTP, passkey login, credential listing/removal, OTP fallback, strict challenge/origin checks, rate limiting, and fake-adapter tests.
Not doingNo passwords, no mandatory passkeys, no passkey-only accounts, no admin-only rollout, no enterprise SSO, and no recovery path that removes OTP.
Success conditions

What must be true when the slice is done.

  • A registered OTP user can add a passkey from /account/security.
  • The user can sign out and sign back in with the registered passkey, without requesting a new OTP.
  • The user can remove the passkey and that credential can no longer sign in.
  • OTP continues to work after adding or removing passkeys.
  • Invalid origin, expired challenge, or replayed assertion does not create a session.

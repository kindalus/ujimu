Slice 15

Podman container deployment

Add the image, environment examples, lifecycle scripts, and documentation needed to run Ujimu as production and test Podman containers.

Scope

What this slice creates

  • A Dockerfile-compatible image for Podman based on node:26-trixie-slim, with Nuxt production output and Gemini CLI.
  • Env example files for production and test profiles.
  • Lifecycle scripts: build, create, deploy, redeploy, and remove.
  • Profile defaults for container names, ports, network, timezone, and persistent mounts.
  • Documentation for manual deployment and safe redeploy.
Runtime contract

One image, two profiles

Productionujimu-prod, host port 3000, host storage under /srv/ujimu/prod.
Testujimu-test, host port 3001, host storage under /srv/ujimu/test.
Container paths/home/ujimu/.pi and /home/ujimu/.local/share/ujimu.
TimezoneTZ defaults to Africa/Luanda and can be overridden.
Acceptance

Success conditions

  • Dockerfile builds an image that runs the Nuxt production server as ujimu:ujimu.
  • The image includes gemini on PATH.
  • Scripts generate correct Podman commands for both prod and test profiles.
  • Redeploy replaces the container without deleting configured host data directories.
  • Test env example enables only existing no-op/mock provider paths and avoids real external provider secrets.
Exclusions

Not part of this slice

  • No CI/CD automation.
  • No reverse proxy, TLS, DNS, or certificate management.
  • No new auth, payment, communication, or Pi provider implementations.
  • No production secret files committed to the repository.
  • No automated real Gemini/API smoke tests requiring external credentials.

Refinement

Sharper direction

  • Use node:26-trixie-slim as the image base; it satisfies the current Node engine floor and matches the requested runtime direction.
  • Use a multi-stage Dockerfile: build with npm ci and npm run build, then copy only runtime output into the final image.
  • Final image should copy Nuxt/Nitro .output and required runtime config only; do not copy full node_modules unless smoke testing proves it necessary.
  • Container listens internally on HOST=0.0.0.0 and PORT=3000; profile scripts only vary the host port mapping.
  • Version prod.env.example and test.env.example; real prod.env/test.env are gitignored and can be overridden with UJIMU_ENV_FILE.
  • Lifecycle scripts create missing profile host directories with mkdir -p but must never delete persistent Pi or Ujimu data.
  • Default image tag is localhost/ujimu:latest, overridable with UJIMU_IMAGE.
  • create.sh fails with a clear message when the target container already exists; replacement belongs to redeploy.sh.
  • deploy.sh creates the container if missing, otherwise restarts the existing container; structural env/volume/port changes require redeploy.sh.
  • redeploy.sh builds, stops/removes any existing container, recreates it, starts it, and never deletes persistent data directories.
  • remove.sh removes only the target container; it does not remove images, networks, env files, or persistent directories.
  • Dockerfile includes a Node-based HEALTHCHECK against http://127.0.0.1:3000/healthz.
  • Add .dockerignore to exclude build output, local dependencies, logs, env files, and real secrets while keeping versioned Pi config resources available.
  • Runtime image installs only minimal Debian packages: ca-certificates and coreutils; healthcheck avoids curl/wget by using Node.
  • test.env.example uses NODE_ENV=development and UJIMU_AUTH_FAKE_DELIVERY_ENABLED=true so existing fake OTP delivery is available without code changes.
  • Usar UJIMU_CONFIG_DIR=/home/ujimu/.config/ujimu para configuração mutável e UJIMU_PI_BUNDLE_DIR=/app/config/pi para recursos Pi versionados.
  • Both production and test env examples enable UJIMU_PI_CONVERSION_ENABLED, UJIMU_PI_INGESTION_ENABLED, and UJIMU_PI_CHAT_ENABLED; external auth/payment/communication stay mocked/no-op only in test.
  • prod.env.example highlights required secrets, but lifecycle scripts do not validate secret completeness; readiness/app checks remain responsible.
  • Optimise for boring, auditable Podman operations rather than a generic orchestration framework.
  • Prefer one runtime contract with profile-specific env files and host mount roots.
  • Keep scripts deterministic and safe: they may create directories/containers, but must not delete persistent data.
  • Use existing app-level mock/no-op behaviour; only wire environment flags needed by the test profile.
